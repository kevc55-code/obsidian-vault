## 1. Sitemap was serving 1,281 redirects, not URLs — fixed, split into an index

`67ca152` (prod) / `49376d2` (staging), 2026-09-14 13:22.

**Found via Coverage:** "Page with redirect" was the single largest non-indexed bucket (501 pages), and Search Console had read the sitemap exactly once — 7 July — and never again in 69 days, while sibling sites get re-read every few days.

**Root cause:** the old sitemap rewrote every URL to end in `/`, but this Next app has `trailingSlash` unset (i.e. `false`) and 308-redirects `/x/` → `/x`. So all 1,281 sitemap URLs pointed at redirects — a sitemap containing zero directly-indexable URLs. Sibling sites on Cloudflare Pages redirect the *other* direction, so the identical normalization logic was correct there — which is exactly why this went unnoticed and why the logic must never be copied between hosts without checking which way each host redirects.

**Fix (`src/lib/sitemap-data.ts`, new):**
- Trailing slashes dropped; sampled URLs verified 200 where the old ones 308'd.
- `lastmod` added to every entry — previously only blog posts had one, leaving ~1,050 URLs with no change signal at all.
- Split into an index: `/sitemap.xml` now points to six section files under `/sitemaps/[section]/route.ts` — core 14, metros 94, guides 51, under-contract 51, blog 320, suburbs 751 (1,281 total, unchanged). `/sitemap.xml` stays the submitted URL so the existing GSC entry stays valid; Google can now re-fetch only the section that changed instead of the whole 1,281-URL blob.
- Hand-rolled rather than Next's `generateSitemaps()`, which "produced no reachable routes here and gives no control over the index URL."

## 2. 535 of 751 suburb pages noindexed — pruning, not consolidation, per [[fsbo-suburb-thin-content]]

`503ab6c` (prod) / `608d4c5` (staging), 2026-09-17 15:06.

This is the resolution of the long-open [[fsbo-suburb-thin-content]] item. The 2026-07-19 fix was enrichment (real Census data per suburb, option (a) in that memory) — this sprint adds option (b), pruning, on top of it, because enrichment alone didn't move indexing: the same 2026-09-14 Coverage export showed 43 metro pages crawled-and-declined and 25 state guides never crawled at all, while all 751 suburb URLs — enriched or not — kept competing for the same crawl allowance Google was rationing.

New `src/lib/suburb-indexing.ts` ships `SUBURBS_WITH_DEMAND`: a hardcoded set of 216 suburb slugs, built from a GSC Pages export (2026-06-14 → 09-12) of every suburb URL with ≥1 real impression in 91 days. Only those 216 stay in the sitemap and stay indexable. The other 535 — which produced **zero** impressions and **zero** clicks over the same 91-day window — get `robots: noindex,follow` and drop out of the sitemap; the pages themselves stay live and linked so link equity still flows up to the parent metro.

The code comment is explicit that this is "triage, not a quality judgement," and flags its own circularity (a page that was never indexed can't earn an impression) — the claim is only that after 91 days these are the URLs with evidence, and evidence is the best tiebreaker available. Refresh cadence noted inline: re-pull the GSC export in about a month; the point is for the allowlist to grow.

## 3. Homepage repositioned: "unbundling" instead of "absence"

`9ff1a08` (prod) / `c9b96ca` (staging), 2026-09-17 21:10.

Not a bug fix — a deliberate copy/positioning change, `src/lib/positioning.ts` + new `src/components/BundleBreakdown.tsx`. Argument in the commit message: "for sale by owner" is the industry's own coinage, and naming the site by that absence concedes the frame (agent-sold is the unmarked default). The replacement isn't "no middleman" either — the site recommends and takes affiliate revenue from flat-fee MLS/attorneys/title companies, so "no middleman" would undercut its own recommendations. The frame instead: a house sale is a bundle of separate jobs with real, separately-priced parts, and this is where you buy the one part you need.

Scoped deliberately narrow — titles, meta, OG and the H1's own text still say "Without an Agent" (that's the term people search), and it still appears ten times on the homepage. Only the *argument* changes: new `BundleBreakdown` table sits above the savings calculator, itemizing each job (pricing, photography, listing, showings, offers, closing) against its standalone price, so the table makes the case and the calculator runs it on the reader's own numbers. Title and escrow deliberately excluded from the pitch — paid either way regardless of FSBO/agent, so including it would overstate the gap. All figures pull from `SavingsCalculator`'s constants via `positioning.ts` so the two can't drift apart.

## 4. New public page: the FSBO Commission Index

`600a4b6` (prod) / `b8c161d` (staging), 2026-09-17 21:46.

A new `/commission-index` page + `/commission-index.csv` route: agent commission cost (both-sides 6% and listing-side-only 3%) expressed in months of local median household income, for 94 US metros (5 Canadian metros excluded — ACS is US-only). Built by `scripts/build-commission-index.js` from Census ACS metro-level (CBSA) data into `src/lib/commission-index-data.json`; `Dataset` JSON-LD, CC-BY license, explicitly framed as free-to-republish link-bait for press/backlinks (`docs/commission-index-pitches.md` — pitch angles, not yet sent as far as this scan can tell).

**Accuracy note worth keeping:** an earlier draft derived metro income by averaging ACS ZIP-level figures across each metro's mapped suburbs — suburbs skew richer than their metro, and it produced obviously-wrong numbers ($109k for Indianapolis, $102k for Pittsburgh). Published version uses the metro-level CBSA figure instead ($73,942 for Pittsburgh). Worth remembering if this pattern — averaging suburb-level data up to a metro claim — shows up again elsewhere in the codebase.
